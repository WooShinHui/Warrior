## Part 1. 컴퓨터 전체 동작 흐름

### 📌 데이터의 여정: SSD → RAM → CPU 캐시 → 레지스터

| 장소 | 뭐가 있나 | 속도 | 크기 |
| --- | --- | --- | --- |
| SSD | 설치된 게임 파일 전부 | ~0.1ms | 수백 GB~TB |
| RAM | 지금 실행 중인 게임 데이터 | ~100ns | 8~64GB |
| L3 캐시 | 자주 쓰는 데이터 (전체 코어 공유) | ~10ns | 8~64MB |
| L2 캐시 | 자주 쓰는 데이터 (코어당) | ~4ns | 256KB~1MB |
| L1 캐시 | 방금 읽은 데이터 (코어당) | ~1ns | 32~64KB |
| 레지스터 | 지금 이 순간 계산 중인 값 | ~0.25ns | 수백 B |
| VRAM (GPU) | 화면에 그릴 것들 (텍스처, 메시) | GPU 전용 | 4~24GB |

**핵심:** CPU는 RAM에서만 읽고, GPU는 VRAM에서만 읽어. 각자 전용 메모리.

### 📌 게임 실행 흐름

1. 더블클릭 → OS가 SSD에서 exe 찾음
2. SSD → RAM으로 프로그램 코드 복사
3. CPU가 RAM에서 명령어 읽기 시작 (Fetch-Decode-Execute)
4. 멀티스레드로 일 분배 (메인/렌더/로딩/오디오/물리)
5. 로딩: SSD → RAM → VRAM 순서로 에셋 올림
6. 매 프레임(16ms): CPU 로직 계산 → GPU에 드로우콜 → 모니터 출력

## Part 2. CPU 내부 구조

### 📌 CPU 핵심 부품

- **CU (제어장치):** 명령 해석 & 지시 ("이건 덧셈이다!")
- **ALU (연산장치):** 실제 계산 수행 (덧셈, 뺄셈, AND/OR)
- **레지스터:** 지금 계산 중인 값 임시 저장 (PC, IR, ACC, SP, MAR, MDR)
- **캐시 L1/L2/L3:** 자주 쓰는 RAM 데이터의 복사본

### 📌 명령어 사이클 (무한 반복)

1. **Fetch:** PC가 가리키는 주소에서 명령어 가져옴
2. **Decode:** CU가 "이건 무슨 연산이야?" 해석
3. **Execute:** ALU가 실제 계산
4. **Store:** 결과를 레지스터나 RAM에 저장

### 📌 파이프라인 & 분기 예측

- **파이프라인:** 여러 명령을 겹쳐서 처리 (세탁기 비유: 세탁+건조+다림질 동시 진행)
- **분기 예측:** if문 결과를 미리 추측. 틀리면 Pipeline Flush (파이프라인 비움)
- **게임 영향:** if(boss->hp<=0) 같은 건 99% FALSE → 예측 정확 → 빠름

### 📌 버스 (부품 간 통신 도로)

- **주소 버스:** "어디?" (주소 전달)
- **데이터 버스:** "뭘?" (실제 데이터 이동)
- **제어 버스:** "읽어? 써?" (읽기/쓰기 신호)
- **PCIe:** GPU와 CPU를 잇는 초고속 버스. SSD(NVMe)도 여기 연결.

### 📌 인터럽트

- **하드웨어 인터럽트:** 컨트롤러 입력, 네트워크 패킷 도착
- **소프트웨어 인터럽트:** 프로그램이 OS에 요청 (System Call)
- **예외:** 0으로 나누기, 잘못된 메모리 접근 → 크래시
- **Page Fault:** 필요한 데이터가 RAM에 없어서 SSD에서 급히 로드 → 미세 끊김

## Part 3. 자료구조 핵심

### 📌 Big-O 속도 비교

| 표기 | 의미 | 데이터 10배 시 | 예시 |
| --- | --- | --- | --- |
| O(1) | 항상 같은 시간 | 그대로 | 배열 인덱스 접근, 해시맵 |
| O(log n) | 반씩 줄여 찾기 | 1.3배 | 이진 탐색, 균형 트리 |
| O(n) | 전부 한 번씩 | 10배 | 리스트 순회, 선형 탐색 |
| O(n log n) | 전부 × 반씩 비교 | 13배 | 정렬 (QuickSort, MergeSort) |
| O(n²) | 모든 쌍 비교 | 100배 | 이중 for문, 무식한 충돌 체크 |

### 📌 배열 vs 연결 리스트

- **배열:** 연속 메모리, 인덱스 접근 O(1), 중간 삽입 O(n), 캐시 효율 높음
- **리스트:** 흩어진 메모리, 삽입/삭제 O(1), N번째 접근 O(n), 캐시 미스 높음
- **게임에서:** 거의 항상 배열(std::vector, TArray) 사용. 캐시 효율 때문.

### 📌 해시맵 (TMap)

- "이름으로 바로 찾기" — O(1) 평균
- 해시 충돌: 같은 칸에 두 개 배정 → 체이닝(리스트 달기)으로 해결
- 게임 사용: 아이템 DB, NPC 대화, 이벤트 매핑

### 📌 우선순위 큐 (Priority Queue)

- "가장 급한 것부터 꺼내기" — 넣기 O(log n), 꼭대기 확인 O(1)
- 내부: Heap(트리를 배열로 구현). 메모리 Heap과 다른 것!
- 게임 사용: A* 길찾기, 이벤트 스케줄러 (3초 후 독 데미지 등)

### 📌 링 버퍼 (Circular Buffer)

- "최근 N개만 기억, 오래된 건 자동 덮어쓰기" — 쓰기/읽기 O(1), 크기 고정
- 게임 사용: 입력 히스토리(콤보 판정), 네트워크 패킷 버퍼, 10초 리플레이

### 📌 비트 플래그 (Bitmask)

- "숫자 하나에 ON/OFF 여러 개 저장" — 확인 O(1), CPU 1클럭
- `독=1, 출혈=2, 동상=4` → "독+동상" = 5 (0101)
- 게임 사용: 상태이상 조합, 충돌 레이어(Collision Channel), 권한 체크

### 📌 UE5 컨테이너: TArray vs TSparseArray vs TMap/TSet

- `TArray`: 연속 메모리 블록. **캐시 적중률** 최상. 순회 최강. 중간 삭제 시 인덱스 당김 비용 O(n).
- `TSparseArray`: 삭제 시 Gap 유지 → 인덱스 안정성 보장, 삭제 O(1). 단, 삭제된 원소 Raw Pointer 접근 시 댕글링 → TWeakObjectPtr 필요.
- `TSet`** / **`TMap`: 해시 테이블 기반 O(1) 접근. 내부적으로 TSparseArray 사용.

> **💡 면접 포인트:** "`TArray`가 왜 캐시 적중률이 높나요?" → CPU가 RAM에서 데이터를 가져올 때 공간 국소성(Spatial Locality) 원리에 따라 인접 데이터를 캐시에 함께 올림. 연속 메모리 배치 = 다음 요소가 이미 캐시에 있을 확률 극대화.

## Part 4. 운영체제

### 📌 프로세스 vs 스레드

|  | 프로세스 | 스레드 |
| --- | --- | --- |
| 메모리 | 독립 (서로 못 봄) | 공유 (같은 프로세스 내) |
| 생성 비용 | 큼 | 작음 (스택만 새로) |
| 크래시 영향 | 해당 프로세스만 | 프로세스 전체 죽을 수 있음 |
| 통신 | 어려움 (IPC) | 쉬움 (변수 공유) |

### 📌 컨텍스트 스위칭

- CPU 코어 1개 = 한 순간에 스레드 1개만 실행
- 교대 시: 레지스터 저장 → 다음 스레드 레지스터 복구 → 실행
- 스레드 너무 많으면: 교대 비용 > 실제 작업 → 오히려 느려짐

### 📌 동기화 & 데드락

- **레이스 컨디션:** 두 스레드가 같은 값 동시 수정 → 값 꼬임
- **Mutex:** "한 명만 들어갈 수 있는 화장실" — lock/unlock
- **Semaphore:** 동시에 N명까지 허용
- **SpinLock:** 잠겨있으면 계속 확인 (짧은 대기용)
- **Atomic:** 읽기+수정+쓰기를 한 번에 (가장 빠름)
- **데드락 조건 4가지:** 상호배제, 점유대기, 비선점, 순환대기

### 📌 가상 메모리 & 페이징

- OS가 각 프로세스에 "독립된 주소 공간" 제공 (가짜 주소)
- 가상 주소 → 물리 주소 변환: MMU + 페이지 테이블 (4KB 단위)
- TLB: 자주 쓰는 매핑 캐시
- Page Fault: 접근한 페이지가 RAM에 없음 → SSD에서 급히 로드
- RAM 부족 → 오래 안 쓴 페이지를 SSD로 내쫓음(스왑) → 느려짐

### 📌 CPU 스케줄링

- Round Robin: 시간 쪼개서 돌아가며 실행 (공평)
- Priority: 우선순위 높은 것 먼저 (게임 모드)
- 선점형: 시간 끝나면 강제 뺏음 (현대 OS 기본)

## Part 5. C++ 핵심

### 📌 Stack vs Heap (메모리 영역)

- **Stack**: 정적 크기, 컴파일 시 결정, 함수 종료 시 스택 포인터 이동만으로 **자동 해제** (초고속).
- **Heap**: 동적 크기, Runtime 할당/해제. 빈 공간 탐색 + 파편화 관리 비용 → 상대적으로 느림.

> **💡 면접 답변:** "스택은 LIFO 구조로 포인터 주소값 하나만 이동시키면 해제 끝. 힙은 빈 공간 탐색 + 파편화 방지 관리 비용이 발생해서 느립니다."

### 📌 얕은 복사 vs 깊은 복사

- **얕은 복사:** 포인터 값(주소)만 복사 → 같은 Heap 공유 → **Double Free 크래시**
- **깊은 복사:** 새 메모리 할당 + 내용물 전부 복사 → 독립. 안전하지만 느릴 수 있음.

### 📌 Lvalue vs Rvalue & 이동 시맨틱 (Move Semantics)

- **Lvalue (좌측값)**: 이름이 있고, 메모리 주소를 취할 수 있으며, 지속되는 변수.
- **Rvalue (우측값)**: 이름이 없고, 표현식 연산 직후 사라지는 **임시 객체(Temporary Object)**.
- **이동(Move) 연산 (**`std::move`** / UE5 `MoveTemp`)**:- 깊은 복사 대신, 임시 객체의 **메모리 소유권(주소)만 신규 객체로 이전** → 복사 비용 제로화.
- 대용량 배열/문자열 전달 시 복사 O(n) → 이동 O(1).

> **💡 면접 답변:** "std::move는 rvalue 캐스팅으로 이동 생성자 호출을 유도합니다. 동적 할당 자원의 소유권 재지정만 수행하므로 비싼 깊은 복사를 원천 차단합니다."

### 📌 값 전달 vs 참조 전달

- **값 전달 (**`FVector Vector`**)**: 객체 전체를 스택에 복사 → 큰 구조체는 복사 비용 큼.
- **참조 전달 (**`const FVector& Vector`**)**: 원본의 메모리 주소(8 bytes)만 넘김. `const`로 원본 보호.
- **기본 타입(**`int32`**, **`float`**)**: 값 전달이 유리 (4바이트 < 주소 8바이트, 간접 참조 비용 없음).

### 📌 가상 소멸자 (Virtual Destructor) ⚠️ 약점 영역

- **원리**: 부모 소멸자에 `virtual` 명시 → 부모 포인터로 자식 삭제 시 **자식 소멸자 → 부모 소멸자** 순서로 정상 호출.
- **위험**: `virtual` 누락 시 부모 소멸자만 호출 → 자식 내부 동적 할당 자원 **메모리 누수**.
- **왜?**: virtual 없으면 컴파일 타임에 **포인터 타입 기준으로 호출할 함수 결정** (vtable 미참조). 부모 타입 포인터 → 부모 소멸자만 호출.
- **UObject 계열**: `UObjectBase`에서 이미 virtual 소멸자 선언됨 → 따로 안 붙여도 됨.

> **💡 30초 답변 템플릿:** "virtual 소멸자가 없으면 컴파일러가 포인터의 정적 타입(부모)에 따라 소멸자를 결정합니다. vtable을 거치지 않으므로 자식 소멸자가 호출되지 않아 메모리 누수가 발생합니다."

### 📌 가상 함수 테이블 (VTable) & 다형성 ⚠️ 약점 영역

- **구조**: `virtual` 함수 포함 클래스 → 객체 메모리 최상단에 `vptr`(8 bytes) 생성 → VTable(함수 포인터 테이블) 가리킴.
- **비용 3가지** (구분해서 설명해야 함):1. **vptr 메모리**: 객체당 8 bytes 추가

1. **간접 참조**: vptr → VTable → 실제 함수 주소 조회 (2단계 점프, 캐시 미스 가능)
2. **인라이닝 불가**: 실행 시점에 호출 대상 결정 → 컴파일러가 인라인 최적화 못 함

> **💡 면접 답변:** "vtable 비용은 세 가지입니다. 첫째 vptr 메모리 8바이트, 둘째 간접 참조로 인한 캐시 미스 가능성, 셋째 런타임 바인딩으로 인라이닝이 불가합니다."

### 📌 인라인 함수 (Inline Function)

- **개념**: 함수 호출 대신 **함수 본문 코드를 직접 삽입(Inlining)** → 호출 오버헤드(스택 프레임 생성, 매개변수 복사, 반환 주소 저장) 제거.
- **컴파일러 거부 케이스**: 코드 너무 길거나, 재귀 호출, virtual 함수(런타임 결정 필요).

### 📌 Const Correctness

- `const` 멤버 함수 (`void GetHealth() const;`): 함수 내에서 멤버 변수 수정 불가를 컴파일러가 보장.
- `mutable` 키워드: const 함수 내에서도 예외적 수정 허용 (스레드 락, 캐싱 목적).

### 📌 RAII (Resource Acquisition Is Initialization)

- **원리**: 자원(메모리, 스레드 락, 파일 핸들)의 소유권을 **객체 생명주기(Scope)**와 일치시킴.
- **동작**: 생성자에서 자원 획득, 소멸자에서 자원 자동 해제.
- **UE5 예시**: `FScopeLock` — 생성 시 Mutex 잠금, scope 벗어나면 소멸자에서 **자동 Lock 해제** → Deadlock 방지.

### 📌 상속 vs 컴포넌트(ECS)

- **상속 한계:** "날으는 마법 기사" = 다중 상속 → 다이아몬드 문제
- **컴포넌트:** 빈 엔티티에 기능(부품)을 조립 → 조합 자유, 클래스 폭발 방지
- **언리얼:** AActor + UActorComponent 구조 = 컴포넌트 패턴 그 자체
- **⚠️ 컴포넌트의 단점** (면접에서 즉답 필요):- 컴포넌트 간 통신 복잡도 증가 (이벤트/인터페이스 필요)
- 캐시 효율 저하 (컴포넌트가 메모리에 흩어짐)

## Part 6. 게임 설계 패턴

### 📌 Object Pool

- **문제:** new/delete 반복 → 느림 + 파편화
- **해결:** 미리 만들어두고 재활용. new/delete 0번. 메모리 고정.
- **사용:** 총알, 파티클, 이펙트, 데미지 숫자 UI

### 📌 FSM (Finite State Machine)

- **용도:** 상태별 행동 분리 (Idle, Chase, Attack, Stagger, Dead)
- **한계:** 상태 20개+ → 전환 조건 n² 폭발 → 관리 불가

### 📌 Behavior Tree

- **FSM 대안:** 매 프레임 트리 꼭대기에서 조건 확인하며 내려감
- **우선순위 기반:** 왼쪽(급한 것)부터 확인 → 성공하면 실행
- **언리얼:** BT 에디터 내장. Task/Decorator/Service/Blackboard

### 📌 이벤트/델리게이트

- **문제:** Player→UI, Sound, Camera 직접 호출 → 결합도 폭발
- **해결:** "맞았어!" Broadcast → 관심 있는 쪽이 알아서 반응 (구독)
- **효과:** 새 시스템 추가 시 기존 코드 수정 0
- **UE5 종류**:- 단일 캐스트 (Single Cast): 1개 함수만 바인딩 (`Execute`)
- 다중 캐스트 (Multi Cast): 여러 함수 일괄 실행 (`Broadcast`)
- 다이나믹 다중 캐스트 (Dynamic): 블루프린트 연동 + 직렬화 가능 (속도는 느림)

> **💡 면접 포인트:** "일반 델리게이트는 C++ 함수 포인터 기반으로 빠르고, 다이나믹은 리플렉션 경유라 느리지만 블루프린트 연결과 직렬화가 가능합니다."

### 📌 Command 패턴

- **핵심:** "행동"을 객체로 만들어 저장
- **사용:** 리플레이, Undo, 입력 버퍼, 네트워크 명령 전송

## Part 7. 네트워크

### 📌 서버-클라이언트 구조

- **Dedicated Server:** 전용 서버 (메이플, 발로란트) — 핵 방지 강함
- **Listen Server:** 한 플레이어가 서버 겸임 (엘든링 협동) — 호스트 유리
- **P2P:** 서버 없음 (격투 게임) — 핵에 취약

### 📌 TCP vs UDP

|  | TCP | UDP |
| --- | --- | --- |
| 도착 보장 | ✅ | ❌ |
| 순서 보장 | ✅ | ❌ |
| 속도 | 느림 | 빠름 |
| 패킷 유실 시 | 재전송 기다림 (Head-of-Line Blocking) | 무시하고 최신만 처리 |

- **게임에서 UDP 쓰는 이유:** 0.1초 전 위치보다 지금 최신 위치가 중요. TCP면 유실 1개 때문에 전체 멈춤.
- **TCP 쓰는 경우:** 채팅, 로그인, 아이템 거래 (유실 불가)

### 📌 클라이언트 예측 & 서버 권위

- **클라이언트 예측:** 서버 응답 전에 로컬에서 먼저 결과 보여줌 → 틀리면 Rollback
- **서버 권위:** 진짜 게임 상태는 서버만 결정. 클라는 입력만 보냄. 핵 방지 핵심.
- **보간(Interpolation):** 받은 두 위치 사이를 부드럽게 (약간 과거, 안전)
- **외삽(Extrapolation):** 마지막 방향으로 예측 (최신, 틀리면 워프)

### 📌 패킷 & 직렬화

- **패킷:** 헤더(보낸곳, 받는곳, 크기) + 페이로드(실제 데이터)
- **직렬화:** C++ 객체 → 바이트 배열 변환 (네트워크 전송용)
- **포맷:** Protobuf(작고 빠름), FlatBuffers(역직렬화 없이 읽기), JSON(느림, 실시간 X)
- **UE5 FArchive**: `operator<<` 연산자로 저장(Save)과 로드(Load)를 단일 코드 구조로 처리 → 읽기/쓰기 순서 불일치(Out of Sync) 방지.

### 📌 UE5 Network Replication & RPC

- `UPROPERTY(Replicated)`: 체력, 탄약, 상태 등 **지속적 변수 데이터**를 서버→클라 동기화.
- **RPC (**`Server`**, **`Client`**, **`NetMulticast`**)**: 발사, 상호작용 등 **일회성 이벤트** 호출.
- **클라이언트 예측 (UE5)**: 네트워크 핑 때문에 클라가 먼저 애니메이션/이펙트 실행(Prediction) → 서버 판정 결과 도착 시 보정(Reconciliation).

> **💡 면접 답변:** "총을 쏠 때 서버 검증만 기다리면 RTT만큼 조작감 악화. 클라가 먼저 이펙트를 선제 실행하고, 서버 판정이 오면 보정합니다."

## Part 8. UE5 C++ 심화

### 📌 UE5 컴포넌트 할당 시점

|  | `CreateDefaultSubobject<T>()` | `NewObject<T>()` |
| --- | --- | --- |
| 호출 위치 | **생성자(Constructor)** 내부에서만 | BeginPlay 등 **런타임 임의 시점** |
| 목적 | CDO 생성 시 컴포넌트 템플릿 기본 세팅 | 액터 스폰 후 동적 추가 |
| 위반 시 | 런타임 호출하면 **엔진 크래시** | - |

### 📌 CDO (Class Default Object)

- 엔진 초기화 시 각 UClass마다 **단 하나만 생성**되는 마스터 기본 객체.
- 신규 액터 스폰 시 CDO의 메모리 블록을 **Fast Binary Copy** → 생성자 재실행 없이 빠르게 복사.
- CDO 수정 시 향후 모든 신규 객체의 기본값에 영향.

> **💡 면접 답변:** "액터 스폰 시 매번 생성자 로직을 실행하지 않고, CDO의 메모리 상태를 이진 복사하여 프레임 드랍(Spike)을 최소화합니다."

### 📌 스마트 포인터 & UPROPERTY() GC

**UObject 계열 (UPROPERTY로 관리):**

- `UPROPERTY()` 명시 → 언리얼 리플렉션 + GC 추적 대상 등록.
- **UPROPERTY 누락 시**: GC가 루트 세트에서 도달 불가능으로 판단 → 사용 중인데도 **강제 수거** → 댕글링 → 크래시.
- `TWeakObjectPtr<T>`: UObject 전용 약한 참조. GC 수거 시 자동 nullptr 처리. `.IsValid()` 검사로 안전 접근.

**Non-UObject (일반 C++ 클래스):**

- `TSharedPtr`: nullptr 가능, 레퍼런스 카운팅 기반 공유. 접근 전 `.IsValid()` 필수.
- `TSharedRef`: **절대 nullptr 불가** 보장. Null Check 오버헤드 제거. nullptr 할당 시 컴파일 에러.
- `TWeakPtr`: 순환 참조 방지용.
- `TUniquePtr`: 단일 소유권.

### 📌 소프트 레퍼런스 vs 하드 레퍼런스

|  | 하드 레퍼런스 | 소프트 레퍼런스 |
| --- | --- | --- |
| 로딩 | 소유자 로드 시 **즉시 함께 로드** | 경로 문자열만 보유, **필요 시 비동기 로드** |
| 장점 | 즉시 사용 가능 | 초기 로딩 시간 단축, 메모리 절약 |
| 단점 | 의존성 연쇄 → 메모리 폭발 | 로드 완료 대기 필요 |

- **사용법**: `FStreamableManager`로 비동기 로드(AsyncLoad) 요청 → 콜백 완료 시 `.Get()` 또는 `.LoadSynchronous()`로 포인터 획득.

### 📌 리플렉션 시스템 (Reflection) & USTRUCT vs UCLASS

- **리플렉션**: C++ 프로그램이 런타임에 자기 자신의 구조(클래스, 프로퍼티, 함수 정보)를 조사·수정할 수 있게 지원.
- **UCLASS**: GC 추적, 리플렉션, 계층 상속, UObject 관리 대상.
- **USTRUCT**: 가벼운 데이터 묶음용. GC에 의해 관리되지 않음. 스택/힙 모두 할당 가능.
- **⚠️ 주의**: USTRUCT 내부의 `UObject*`에 `UPROPERTY()` 붙이면, 해당 구조체가 UCLASS의 UPROPERTY로 소유되어 있을 때 GC 추적 작동함.

### 📌 UE5 빌드 시스템 (UHT vs UBT)

- **UHT (Unreal Header Tool)**: `UCLASS()`, `UPROPERTY()` 매크로 분석 → 리플렉션 코드(`.generated.h`) 자동 생성.
- **UBT (Unreal Build Tool)**: 생성된 코드 + 엔진 소스를 엮어 C++ 컴파일러 호출, 빌드 총괄.
- `.generated.h`** 위치**: 반드시 헤더 최하단 `#include`에 위치 — UHT가 위의 매크로 정보를 기반으로 생성하므로.

### 📌 UE5 틱 그룹 (Tick Group) & Execution Order

- `TG_PrePhysics`: 물리 연산 전 (입력, AI 판단)
- `TG_DuringPhysics`: 물리 연산 실행 중 병렬 처리
- `TG_PostPhysics`: 물리 완료 후 (카메라 추적, 위치 동기화)

> **💡 면접 포인트:** "카메라를 PostPhysics에 배치해야 캐릭터 위치 업데이트 완료 후 추적합니다. 안 그러면 1프레임 전 위치를 카메라가 추적해서 Jittering 발생."

### 📌 멀티스레딩: FRunnable & Task Graph

- `FRunnable`: 장시간 독립적인 전용 Worker Thread 직접 생성/제어.
- **Task Graph**: 짧은 작업들을 의존성 그래프로 묶어 엔진 스레드 풀에 비동기 분배.
- **⚠️ 금지**: Worker 스레드에서 `UObject` 생성/레벨 액터 수정 금지. 엔진 핵심 로직은 **GameThread에 단일 소유권** → 타 스레드에서 직접 수정 시 Race Condition + 크래시. 비동기 완료 후 결과를 GameThread로 전달.

### 📌 메모리 파편화 (Memory Fragmentation)

- **개념**: new/delete 반복 → 총 가용 메모리는 충분하지만 **연속된 공간 부족** → 할당 실패.
- **UE5 대응**: 자체 메모리 할당자(`FMallocBinned`)로 크기별 Bin 미리 확보 → 파편화 방지.
- **예방법**: Object Pooling + `TArray::Reserve()`로 재할당 억제.

### 📌 캐시 국소성 (Cache Locality)

- **시간 국소성 (Temporal)**: 최근 접근한 위치에 곧 다시 접근 (반복문 변수)
- **공간 국소성 (Spatial)**: 인접 메모리를 곧 접근 (TArray 연속 배치)
- **DOD (Data Oriented Design)**: 포인터 기반 파편화 객체 대신, 관련 데이터를 연속 배열로 몰아넣어 캐시 효율 극대화.

### 📌 Collision Channels & Trace

- **LineTraceSingleByChannel**: 반응 방식(Ignore/Overlap/Block) 채널 기준 충돌 검사.
- **LineTraceSingleByObjectType**: 물성 유형(Static, Dynamic, Pawn) 기준 충돌 검사.
- **최적화**: Complex Mesh 대신 Simple Collision(Box/Sphere) 사용 + 불필요 채널 Ignore 설정 + BVH 공간 분할.

### 📌 UE5 Rendering Pipeline & Draw Call

- **Draw Call**: CPU가 GPU에게 "이 메시+재질을 그려라" 명령 단위. 많을수록 CPU 오버헤드 급증.
- **ISM/HISM**: 동일 메시를 하나의 Draw Call로 묶어 그리기.
- **Nanite**: 가상화된 폴리곤 스트리밍. LOD 수작업 없이 실시간 메시 세밀도 제어 + Draw Call 자동 최적화.
- **Lumen**: 실시간 글로벌 일루미네이션(GI). 텍스처 베이킹 없이 동적 조명 연산.

### 📌 GAS (Gameplay Ability System)

- **GameplayAttribute**: HP, MP, 이동속도, 공격력 등 수치 스탯.
- **GameplayEffect**: 스탯 변경, 버프/디버프, 데미지 연산을 적용하는 데이터 로직 단위.
- **역할 분담 이유**: 데이터(Attribute)와 로직(Effect)의 완전한 디커플링 → 유연성 확보.

> **💡 면접 답변:** "Effect를 거쳐야 클라이언트 예측, 네트워크 동기화, 데미지 저항 계산, 버프 중첩 등을 한 곳에서 안전하게 처리하고 일관성을 유지할 수 있습니다."

### 📌 크래시 디버깅 & Call Stack 분석

- **도구**: Call Stack, `.dmp` (Crash Dump), PDB (Symbol File).
- **절차**: 덤프 + PDB 연결 → 기계어 주소를 함수 이름·줄 번호로 복원(Symbolication) → 크래시 지점 변수 상태 파악.
- `0x00000000` = Null Pointer Dereference.
- AddressSanitizer(ASan), Unreal Insights, `MemReport` 활용.

### ⚠️ 유형 2: 존재는 아는데 이름/구조를 모르는 것

- 공간 분할 자료구조: QuadTree(2D)/Octree(3D) — 영역을 재귀적으로 4/8분할, 근처 오브젝트만 검색 → O(n²)→O(n log n)
- 시간복잡도 계산: "누가 누구와 비교하는지" 주어 정확히 파악
- `emplace_back` vs `push_back` vs `reserve`:- `push_back`: 객체 생성 후 복사/이동해서 넣기
- `emplace_back`: 벡터 안에서 직접 생성 (복사/이동 0)
- `reserve`: 미리 capacity 확보 (재할당 방지)

### ⚠️ 유형 3: 개념은 아는데 자신 있게 설명 못하는 것

- 깊은 복사 구현: "새 메모리 할당 + memcpy or 요소별 복사"
- TCP/UDP 용어: Head-of-Line Blocking, 자체 신뢰 계층
- 컴포넌트 패턴 단점: 컴포넌트 간 통신 복잡도, 캐시 효율 저하
