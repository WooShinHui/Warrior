## Part 1. C++ / 언리얼 메모리 기초

### Q1. 스마트 포인터

**질문**: unique_ptr, shared_ptr, weak_ptr을 각각 언제 쓰나요? shared_ptr 두 개가 서로 참조하면 왜 문제인가요? 

**정답**: unique_ptr=단독 소유권. shared_ptr=참조카운트 기반 공유 소유권, 카운트가 0이 될 때 해제. 두 shared_ptr이 서로를 참조하면(순환 참조) 서로가 서로를 붙잡고 있어 카운트가 절대 0이 안 되어 메모리 누수 발생. weak_ptr은 카운트를 증가시키지 않고 관찰만 하므로 순환 참조 해결에 씀. **메모**: 개념 정확. "참조카운트가 중복된다"는 표현만 "서로 붙잡고 안 놔준다"로 정정.

### Q2. 가상함수 / vtable

**질문**: 가상함수를 쓰면 컴파일러 입장에서 뭐가 달라지나요? 

**정답**: 부모가 선언한 가상함수는 vtable(함수 포인터 테이블)을 거쳐 런타임에 실제 객체 타입의 함수를 호출. 일반 함수보다 테이블 조회 비용이 한 번 더 듦. 추가로, 간접 호출이라 컴파일러가 인라인 최적화를 못 하는 경우가 많음. **메모**: 정확.

### Q17. TSharedPtr vs std::shared_ptr, UObject 구분

**질문**: 왜 언리얼은 자체 TSharedPtr을 따로 만들었나요? **

정답**: **UObject 계열은 TSharedPtr로 감싸면 안 됨** — UObject는 UPROPERTY+GC로만 관리. TSharedPtr은 UObject가 아닌 일반 C++ 클래스/구조체용 참조카운팅 포인터. UE가 따로 만든 이유는 플랫폼별 커스텀 할당자 통합, 스레드 안전 모드 선택(ThreadSafe/NotThreadSafe) 등. 

**⚠️ 주의**: 처음에 TSharedPtr과 UPROPERTY/GC를 같은 시스템으로 혼동함. **완전히 별개 시스템**이라는 것 재확인 필요. UObject를 TSharedPtr로 감싸는 건 안티패턴(이중 해제 위험).

### Q21. 가상 소멸자

```cpp
class Base { public: ~Base() {} };
class Derived : public Base { public: ~Derived() { /* 리소스 해제 */ } };
Base* obj = new Derived();
delete obj; // 문제는?
```

**정답**: Base 소멸자가 virtual이 아니면, delete 시 어떤 소멸자를 부를지 obj의 __컴파일 타임 타입(Base_)_* 기준으로 정적 결정됨 → Derived::~Derived()가 안 불려서 리소스 누수. virtual을 붙이면 vtable을 거쳐 실제 객체 타입(Derived)부터 소멸자 체인이 호출됨. (C++ 표준상 이 상황은 정의되지 않은 동작(UB).) **메모**: 결론은 정확. "delete가 포인터 변수 자체를 지운다"가 아니라 "메모리를 반납할 뿐, 어떤 소멸자 코드를 실행할지가 문제"라는 점 명확히.

### Q39. 오버로딩 vs 오버라이딩

**정답**: 오버로딩=같은 클래스 안에서 이름은 같고 매개변수(타입/개수)가 다른 함수 여러 개. **컴파일 타임**에 인자 보고 확정. 오버라이딩=자식이 부모 가상함수를 재정의, **런타임**에 vtable로 결정. → 21번과 연결: virtual 없는 소멸자는 오버라이딩이 아니라 "이름만 같은 별개 함수"처럼 정적 처리되어버리는 것. 
**⚠️ 주의**: 처음엔 오버로딩 개념 자체를 몰랐음 → 새로 학습 완료.

### Q26. 메모리 패딩

```cpp
struct A { char c; int i; char c2; };  // ?
struct B { int i; char c; char c2; };  // ?
```

**정답**: char=1바이트, int=4바이트. CPU는 타입 크기의 배수 주소에서 읽는 걸 선호(정렬 요구사항) → 컴파일러가 패딩 삽입. A: c(1)+패딩(3)+i(4)+c2(1)+패딩(3) = **12바이트**. B: i(4)+c(1)+c2(1)+패딩(2) = **8바이트**. → A가 더 큼. 실무 규칙: 큰 멤버부터 작은 멤버 순으로 선언하면 패딩 최소화.

**메모**: 결론(A>B)은 처음부터 정확. char/int 크기값 및 패딩 원리는 재확인 후 이해 완료.

### Q28. 정수 오버플로우

**질문**: uint8(0~255)에 255+1을 하면?

**정답**: 부호 없는 8비트는 11111111(255)에서 +1 하면 비트가 다 차서 **0으로 wrap-around**. 유명 사례: 팩맨 Level 256 킬 스크린 버그(스테이지 번호가 8비트라 255를 넘으며 오버플로우, 화면 렌더링이 깨짐). **메모**: 처음엔 몰랐음 — 신규 학습.

### Q34. const 참조 매개변수

```cpp
void PrintHealth(const Enemy& enemy) { ... }
```

**질문**: 왜 `Enemy&`가 아니라 `const Enemy&`로 받나요

**정답**: (1) 컴파일러가 함수 내에서 실수로 원본을 수정하는 코드를 컴파일 에러로 막아줌. (2) const 객체도 인자로 넘길 수 있게 해줌(const가 없으면 const 객체를 못 넘김). **⚠️ 주의**: "의도"는 맞혔으나 "안 붙이면 어떤 위험이 있는지"에 대한 직접 답이 빠졌었음.

### Q40. 얕은 복사 vs 깊은 복사

```cpp
class Inventory {
    int* items;
public:
    Inventory(const Inventory& other) { items = other.items; }
};
```

**정답**: 주솟값만 그대로 복사(얕은 복사) → a, b가 같은 메모리를 가리킴 → 하나가 소멸(delete)하면 나머지는 댕글링 포인터. **raw pointer는 참조카운트 기능이 없음** — shared_ptr 같은 스마트 포인터 클래스가 내부적으로 그 로직을 구현해놨을 때만 자동 카운팅됨.

해결: 깊은 복사를 직접 구현하거나 스마트 포인터 사용. **메모**: 스스로 "왜 참조카운트가 안 오르냐"는 질문까지 던지고 정확히 이해함 — 우수.

### Q44. 댕글링 포인터

```cpp
int* ptr = new int(5);
delete ptr;
*ptr = 10; // ?
```

**정답**: delete는 **메모리를 반납할 뿐 포인터 변수(ptr) 자체를 지우지 않음** — ptr은 여전히 같은 주소를 들고 있음(무효화된 주소). `*ptr=10`은 정의되지 않은 동작(크래시/조용한 오염 등 예측 불가). 안전 처리: `delete ptr; ptr = nullptr;` 관용구 — 이후 실수로 접근하면 즉시 명확한 크래시가 나서 디버깅이 쉬움. 근본 해결은 스마트 포인터.

**⚠️ 주의**: "포인터가 없어졌다"는 표현 정정 — 변수는 남아있고 가리키는 대상만 무효화됨.

## Part 2. 자료구조 / 알고리즘

### Q6 / Q20. 공간 분할 자료구조

**질문**: 반경 내 적을 빠르게 찾으려면? A_에서 우선순위 큐를 쓰는 이유는? *

정답**: 2D는 쿼드트리(4등분), **3D는 옥트리(8등분) 또는 공간 해시 그리드**(실무에서 더 흔함, 구현 간단, 삽입/삭제 빠름). A_는 "f값이 가장 작은 노드"를 매 스텝 꺼내야 하는데, 배열 전체 순회는 O(n), **최소 힙(우선순위 큐)은 최솟값 추출이 O(log n)**.

**⚠️ 주의**: 3D 게임인데 쿼드트리(2D 전용)라고 답함 → 옥트리/공간해시로 정정 필요. 우선순위 큐를 "선입후출(스택)"로 착각 → **"최솟값 우선 추출" 구조**임을 재확인.

### Q8. 캐시 지역성

**질문**: 배열 vs 링크드리스트, 캐시 히트율은? *

정답**: **배열이 캐시 히트율 높음** — 메모리에 연속 배치되어 캐시라인 단위로 미리 로드됨. 링크드리스트는 노드가 각각 따로 할당되어 메모리상 흩어져 있어 next 포인터 따라갈 때마다 캐시 미스 가능성 높음. Big-O(둘 다 순회 O(n))와 실제 벽시계 시간은 다른 얘기 — Big-O는 "연산 횟수"만 재지 캐시 미스 비용은 안 봄. *

⚠️ 주의**: **개념이 완전히 반대로 되어 있었음** — 배열=인덱스 O(1) 접근/캐시 좋음, 링크드리스트=임의접근 O(n)/캐시 나쁨으로 정정 완료. 실제 면접에서 나올 경우 절대 헷갈리면 안 되는 항목.

### Q13. 해시맵 평균 vs 최악 복잡도

**정답**: 평균 O(1)이지만, 서로 다른 키가 같은 해시값으로 충돌(해시 충돌)하면 같은 버킷에 몰려 링크드리스트처럼 순회해야 해서 최악 O(n)까지 감.

**메모**: 정확.

### Q14. BST가 O(log n)이 안 되는 경우

**정답**: **입력이 이미 정렬된 순서로 하나씩 삽입될 때**(예: 1,2,3,4,5 순서로 insert) — 트리가 한쪽으로만 자식을 갖는 링크드리스트 형태가 되어 높이가 n이 됨 → O(n). *

⚠️ 주의**: 원인을 "배열이 정렬 안 됨"으로 반대로 답함 → **"이미 정렬된 순서로 삽입됨"**이 정확한 원인.

### Q42. 이분 탐색

**정답**: 정렬된 배열에서 중간값과 비교해 매번 탐색 범위를 절반으로 줄임 → n개에서 1개 남을 때까지 나누는 횟수가 log₂n번 → O(log n). *

정렬 안 된 배열에서는 사용 불가**. **메모**: 정확.

### Q36. TArray 동적 크기 증가

**정답**: 매번 1칸씩 재할당하면 원소 복사 비용이 누적되어 총 O(n²). *

여유분을 배로 늘리는 방식(capacity 2배씩)**으로 하면 재할당이 드물어져 평균(상환 분석) O(1)에 가까워짐. reserve()로 미리 크기를 예약해두는 것도 같은 원리(재할당 자체를 없앰). **메모**: reserve/emplace_back과의 연결까지 스스로 도출 — 정확.

## Part 3. 컴퓨터 구조 / OS / 네트워크

### Q7. 스택 vs 힙

**정답**: 스택=함수 스코프 벗어나면 자동 해제(휘발성), 힙=명시적 해제 없으면 계속 남음(누수 위험). new 남발 시 (1) 메모리 파편화로 캐시 히트율 감소, (2) 힙 할당 자체가 스택보다 비쌈(빈 블록 탐색 필요)

**메모**: 정확.

### Q9. 프로세스 vs 스레드

**정답**: 프로세스=독립적으로 돌아가는 개별 프로그램(메모리 비공유). 스레드=한 프로세스 안에서 메모리 공유. 단일 스레드로 렌더링/물리/오디오를 다 처리하면 CPU 낭비 + 하나가 오래 걸리면 나머지도 다 밀림(지연시간 격리 실패). 멀티스레드 시 공유 메모리 침범 방지를 위해 mutex로 락. 

**메모**: 정확. 데이터 레이스까지 스스로 연결한 것 우수.

### Q10. TCP vs UDP

**정답**: TCP=도착 보장(채팅, 상점 거래 등에 사용), 단 Head-of-Line Blocking 이슈. UDP=패킷 유실돼도 다음 패킷 계속 진행, 액션 게임처럼 끊김이 UX를 해치는 경우 선호. *

메모**: 신입 기준 이상. HoL Blocking까지 짚음.

### Q16. 클라이언트 예측 / 랙 보상

**질문**: 서버 응답을 기다렸다가 캐릭터를 움직이면 왜 문제인가요? 

**정답**: 매번 서버가 이동 유효성을 검증하면 레이턴시 누적 → UX 저하. 그래서 클라이언트 이동은 서버 응답 없이 즉시 처리(클라이언트 예측). 단 FPS처럼 서로의 좌표에 사격하는 경우, 서버가 값을 받았을 때 걸린 레이턴시만큼 되돌려 판정하는 **랙 보상(lag compensation)**을 적용. **메모**: 정확.

### Q25. 델타타임

**질문**: `Location += Speed` (DeltaTime 없이) 하면?

**정답**: 프레임률에 이동 속도가 종속됨 — 60fps 기기는 30fps 기기보다 초당 2배 더 이동(속도가 실질적으로 2배가 됨). DeltaTime을 곱해야 프레임률과 무관하게 "초당 이동 거리"가 일정하게 유지됨. **메모**: 정확.

### Q32. 프레임 예산

**정답**: 60fps 유지하려면 프레임당 **16.67ms**. 렌더링/물리/AI/로직 합이 이 예산을 넘기면 프레임드랍 발생.

**메모**: 정확.

## Part 4. 언리얼 엔진 실전

### Q3. GC / UPROPERTY

**질문**: 왜 UE는 표준 스마트 포인터 대신 자체 GC를 쓰나요? UPROPERTY의 역할은? 

**정답**: UObject 그래프는 순환 참조(Actor↔Component 등)가 일상적이라 참조카운팅(shared_ptr류)에 취약 → UE는 **도달 가능성 분석(mark-and-sweep 계열) GC**를 자체로 씀. UPROPERTY는 단순 "변수 선언 알림"이 아니라 **GC가 그 포인터를 추적 대상(살아있는 참조)으로 등록**하는 것 — 안 붙이면 GC가 그 오브젝트를 회수해버려 포인터가 댕글링됨.

**⚠️ 주의**: 처음엔 "자체 GC가 있다" 정도만 알았음 — 원리와 UPROPERTY 역할 재학습 완료. **17, 24, 38번과 한 시스템(리플렉션)으로 연결됨.**

### Q4. Actor-Component vs GameObject-MonoBehaviour

**정답**: Unity=GameObject 상속 없이 순수 합성(컴포넌트만 붙임). UE=AActor를 **상속**(APawn, ACharacter 등)한 뒤 그 위에 Component를 **합성** — 상속+합성 혼합 구조. Unity는 애초에 "상속으로 갈지 컴포넌트로 갈지" 선택지가 없음(항상 컴포넌트).

**메모**: 붙였다 뗄 수 있는 구조라는 설명은 정확했으나, "상속 구조 관점"이 처음엔 빠져있었음 — 보강 완료.

### Q5 / Q22. GAS (GameplayAbility/Effect/AttributeSet)

**정답**: GA=행동(공격/액션/사망), GE=상태 변화(버프/디버프/데미지), AttributeSet=데이터, Cue=이펙트+사운드, Tag=현재 행동 상태(행동 간 개입 차단/블렌드).

**왜 캐릭터 클래스에 안 넣고 쪼개나**: (1) 데이터-로직 분리로 기획자가 재컴파일 없이 수치 조정 가능, (2) 멀티플레이 복제(Replication)를 GAS 프레임워크가 자동 처리, (3) 재사용성(같은 GA를 플레이어/몬스터 모두에 부착 가능). 

**Instant vs Duration/Infinite 내부 설계 차이**: Instant는 적용 순간 값 한 번 바꾸고 끝(추적 불필요), Duration/Infinite는 "지금 활성 상태인가"를 계속 추적해야 해서 별도의 ActiveGameplayEffect 객체로 생명주기 관리 필요. **메모**: GAS 요소별 "무엇"은 정확했으나 처음엔 "왜 쪼갰는지"가 빠져있었음 — 보강 완료.

### Q19. 언리얼 RPC

**정답**: Server RPC=클라이언트가 호출→**서버**에서 실행. Client RPC=서버가 호출→**소유 클라이언트**에서 실행. NetMulticast RPC=서버가 호출→**서버+모든 클라이언트**에서 실행. Server RPC를 무검증으로 열면 클라이언트가 조작된 값(데미지 9999 등)을 보낼 수 있어 **서버 쪽에서 반드시 값의 유효성을 재검증**해야 함(클라이언트 입력을 그대로 신뢰하지 않는다는 원칙).

**⚠️ 주의**: 멀티플레이 프로젝트 미경험으로 답변 보류 — 정직한 태도. 개념만 새로 학습.

### Q23. 싱글턴 안티패턴

**정답**: Unity의 `static Instance`는 씬 전환에도 살아있다는 전제인데, UE는 레벨 전환 시 그 레벨 종속 오브젝트가 통째로 파괴됨 → static 포인터가 파괴된 오브젝트를 계속 가리키는 댕글링 위험. 또한 static Instance는 UE의 GC 추적 대상 밖이라 위험. UE는 이미 GameInstance(레벨 전환에도 안 죽는 전역), Subsystem(자동 생명주기+GC 통합) 등 정식 전역 접근 시스템을 제공하므로 그걸 쓰는 게 정석.

**⚠️ 주의**: "왜"에 대한 답이 처음엔 "메모리 누수?" 정도로 막연했음 — 정확한 이유 보강.

### Q24. Cast<> vs dynamic_cast

**정답**: dynamic_cast는 표준 RTTI 사용 — 엔진은 성능상 RTTI를 꺼두는 경우 많아 아예 못 쓸 수 있음. UE는 UObject용 **자체 리플렉션 메타데이터**(UPROPERTY/UCLASS로 빌드 시 생성)를 조회해서 캐스팅 — RTTI 꺼도 동작, 블루프린트 연동됨. **3번(GC), 38번(UFUNCTION)과 같은 리플렉션 시스템의 다른 얼굴.** 

**⚠️ 주의**: 처음엔 몰랐음 — 신규 학습, UE 정체성에 가까운 핵심 개념이므로 꼭 숙지.

### Q27. TArray / TMap / TSet

**정답**: 전체 순회하며 데미지 주기(적 리스트)=**TArray**(인덱싱 접근만 하면 됨). 특정 ID로 빠르게 찾기(세션 정보)=**TMap**(해시 기반 빠른 검색). **메모**: 정확.

### Q30. 컴포넌트 간 통신

**질문**: HealthComponent가 체력 0이 됐을 때 PlayerCharacter의 사망 처리를 어떻게 부르나요? **정답**: HealthComponent가 사망 델리게이트를 브로드캐스트하고, PlayerCharacter가 그 델리게이트를 구독. 서로 직접 참조/결합하지 않고도 통신 가능(결합도 낮춤). **메모**: 15번(보스 예시)의 원리를 정확히 재적용 — 우수.

### Q31. 인터페이스 vs 상속 vs 컴포넌트

**정답**: 상속=클래스의 "정체성"(뭐냐), 인터페이스=클래스의 "능력"(뭘 할 수 있냐). 문/상자/NPC처럼 서로 다른 부모를 가진 클래스에 공통 행동(상호작용 가능)만 얹고 싶을 때, 억지로 공통 부모로 다중상속(다이아몬드 문제 위험)하기보다 인터페이스(IInteractable)로 계약만 강제하는 게 안전. 컴포넌트는 실제 구현 로직까지 포함한 재사용 가능한 실체라는 점에서 인터페이스와 다름 — 실무에서는 "무엇을 할 수 있는가=인터페이스", "판정 등 공통 로직=컴포넌트"로 함께 사용.

**메모**: "컴포넌트로 대체 가능하지 않냐"는 좋은 추가 질문 — 인터페이스(계약)와 컴포넌트(실제 구현체)의 역할 차이로 정리 완료.

### Q33. static 멤버 변수

```cpp
class Enemy { static int enemyCount; public: Enemy() { enemyCount++; } };
```

**정답**: static이 없으면 인스턴스마다 각자 별도의 변수를 가짐 → 각 객체의 카운트가 다 1일 뿐, "총 개수"가 안 됨. static 멤버는 **클래스 전체에 딱 하나만 존재**하는 저장 공간이라, 모든 인스턴스의 생성자가 같은 하나의 변수에 값을 누적함.

**⚠️ 주의**: "포인터를 공유한다"는 비유를 정정 — 포인터가 아니라 애초에 "그 변수 자체가 인스턴스 안에 존재하지 않고, 전역 공간에 하나만 존재"하는 것.

### Q35. BeginPlay vs 생성자

**질문**: BeginPlay와 생성자를 왜 나눴나요? **정답**: 생성자 시점엔 레벨의 다른 액터들이 아직 다 스폰 안 됐을 수 있음 → 그 시점에 다른 액터를 참조하면 nullptr 위험. BeginPlay는 **레벨의 모든 액터가 스폰 완료된 후** 호출되므로, 다른 액터 참조/게임 상태 초기화는 반드시 BeginPlay에서 해야 안전.

**⚠️ 주의**: 처음엔 "레벨 스트리밍(램 절약)" 얘기로 답함 — 맞는 지식이지만 질문의 정확한 초점(생성자 vs BeginPlay 시점 차이)이 아니었음. 질문의 정확한 초점을 벗어나는 대표 사례.

### Q37. 델리게이트가 불리한 경우

**정답**: 델리게이트는 "이산적(가끔 발생하는) 이벤트"에 최적. **연속적으로 계속 변하는 값**(예: 매 프레임 갱신되는 플레이어와의 거리 표시 UI)은 억지로 델리게이트로 감싸면 오히려 복잡해짐 → 이런 경우는 Tick(폴링)이 더 자연스러움. 델리게이트 자체도 등록/해제 관리, 중복 등록 방지 비용이 있음(관리 오버헤드). 

**메모**: "폴링이 낫다는 게 아니라 상황별로 나눠 써야 한다"는 정정이 정확. 처음엔 델리게이트가 무조건 낫다는 뉘앙스였으나, 구체적 반례 도출 완료.

### Q38. UFUNCTION / 리플렉션

**정답**: 블루프린트는 C++ 컴파일 결과(기계어)를 직접 못 읽음 — 블루프린트 VM은 **UE 리플렉션 메타데이터**를 보고 함수 존재/파라미터/호출법을 앎. UFUNCTION() 매크로는 빌드 시 UnrealHeaderTool이 그 함수를 파싱해 메타데이터에 등록하게 함. UFUNCTION 없는 함수는 메타데이터에 없어 블루프린트에서 호출 불가.

**메모**: "C++ 함수는 언리얼이 못 읽는다"는 결론은 정확, 리플렉션 메커니즘까지 보강 완료.

### Q41. Pawn vs Character (+추가질문: 비행기 탑승 구현)

**정답**: 둘 다 조종(Possess) 가능 — 차이는 "조종 가능 여부"가 아니라 **이동 로직 보유 여부**. ACharacter는 CharacterMovementComponent(걷기/점프/중력/경사면 등)+캡슐 콜리전을 기본 장착. APawn은 아무 이동 로직도 없는 최소 뼈대 — 비행기/차량/고정 포탑처럼 걷기 로직이 필요 없거나 방해되는 경우 Pawn을 직접 상속. **탑승 구현**: Character가 Pawn으로 "변신"하는 게 아니라, **PlayerController가 UnPossess()→Possess(VehiclePawn)로 조종 대상을 갈아탐**. 기존 Character는 파괴되지 않고 숨김 처리(SetActorHiddenInGame + 콜리전 off) 후 하차 시 다시 Possess. 

**⚠️ 주의**: 처음엔 "Pawn이 상위개념, Character는 조종 가능"으로 다소 부정확한 기준 — "이동 로직 재사용 여부"로 정정. 탑승 구현 추가질문에 스스로 좋은 지점을 짚어 심화 학습 완료.

### Q43. 애니메이션 블렌딩

**정답**: Blend Space에서 파라미터(보통 이동 속도)에 따라 애니메이션 비율을 자동 보간 — 속도 0=Idle, 200=걷기, 500=달리기 사이를 부드럽게 섞음. (Spine에서는 "믹스 값"으로 부르던 것과 동일 개념.)

**메모**: 정확.

### Q45. Actor vs Component (무기 장착)

**정답**: 월드에 독립적으로 존재해야 함(주울 수 있음, 바닥에 떨어뜨림, 자체 물리 충돌 필요)→**Actor**. 캐릭터에 영구 부착이고 독립 충돌/생명주기가 필요 없음→**Component**(StaticMeshComponent 등, 더 가볍고 간단).

**메모**: 정확, 판단 기준도 실무적.

## Part 5. 종합 적용 문제

### 최종 통합 문제 (GAS 재설계)

**질문**: "캐릭터 클래스 하나가 이동·전투·스태미너·사망을 전부 떠맡던" UE5 프로젝트를 GAS로 다시 설계한다면, 각 책임을 어떤 시스템/클래스로 나누고, 왜 나은지 GAS 3요소 등 오늘 배운 개념 2개 이상과 연결해 설명. **모범 답**: 캐릭터 클래스는 얇게 유지, 이동=MovementComponent, 전투=CombatComponent(GA 보유), 체력/스태미너=**AttributeSet**. 스태미너 소모나 화상 틱 데미지는 **GameplayEffect**로 처리. 체력이 0이 되면 AttributeSet의 OnHealthChanged **델리게이트**가 발화해 Input/애니메이션/HUD 컴포넌트가 각자 구독해 반응 → 결합도 낮음 + AI 몬스터에도 동일 컴포넌트 재사용 가능.

**⚠️ 주의**: 답변에서 GAS 3요소(GA/GE/AttributeSet) 키워드가 빠짐 — **질문이 명시한 키워드를 반드시 짚어주는 습관** 필요. 이번 세션 전체에서 가장 반복된 패턴(질문의 정확한 초점을 벗어나는 것)이 마지막까지 재현됨 — 실전 최우선 개선 포인트.
