## 1. Stack vs Heap (메모리 영역)

### 📌 핵심 정리
* **Stack**: 
  * **특징**: 메모리 크기가 정적(Static)이며 컴파일 시점에 결정됨.
  * **해제**: 함수 탈출 시 스택 포인터가 이동하며 **자동 해제** (속도 매우 빠름).
* **Heap**: 
  * **특징**: 메모리 크기가 동적(Dynamic)이며 실행 시점(Runtime)에 할당/해제됨.
  * **해제**: 프로그래머의 명시적 해제(`delete`) 또는 **Garbage Collector(GC)**가 수거 (속도 상대적으로 느림).

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 스택(Stack)은 왜 해제 속도가 빠르고, 힙(Heap)은 왜 상대적으로 느린가요?**
* **A**: 
  * **Stack**: LIFO(후입선출) 구조로 입출구가 하나입니다. 함수 종료 시 **스택 포인터 주소값 하나만 이동시키면 메모리 해제가 끝나므로** 연산 비용이 오버헤드 없이 매우 적습니다.
  * **Heap**: 메모리 빈 공간을 탐색하여 할당하는 과정과, 사용 완료 후 구멍 난 공간을 정리(파편화 방지)하는 관리 비용이 발생하여 속도가 상대적으로 느립니다.

> **Q. C++ `new`/`delete`로 할당하는 힙과 언리얼 `UPROPERTY()` GC가 관리하는 힙 영역은 서로 다른 영역인가요?**
* **A**: 동일한 힙 영역입니다. 다만 언리얼은 `UObject` 계열을 관리하기 위해 기본 C++ 힙 위에 **자체 가비지 컬렉션 관리 레이어**를 구성하여 메모리를 추적 및 수거합니다.

## 2. UE5 컴포넌트 할당 시점 (CreateDefaultSubobject vs NewObject)

### 📌 핵심 정리
* **`CreateDefaultSubobject<T>()`**:
  * **호출 위치**: 오직 클래스 **생성자(Constructor)** 내부에서만 사용.
  * **목적**: CDO(Class Default Object) 생성 시점에 컴포넌트 템플릿을 기본 세팅.
* **`NewObject<T>()`**:
  * **호출 위치**: `BeginPlay()` 등 **런타임 임의 시점**.
  * **목적**: 액터가 이미 스폰된 후, 동적으로 새로운 컴포넌트/오브젝트를 추가·생성할 때 사용.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. `BeginPlay()` 같은 런타임 시점에 `CreateDefaultSubobject`를 호출하면 어떻게 되나요?**
* **A**: **엔진 크래시(Crash)가 발생**합니다. `CreateDefaultSubobject`는 엔진 초기화 단계에서 CDO(기본 객체)를 구성하는 용도이므로 생성자 내부 호출로 엄격히 제한되어 있습니다.

## 3. 값 전달(Value) vs 참조 전달(Reference)

### 📌 핵심 정리
* **값 전달 (`FVector Vector`)**:
  * **원리**: 매개변수로 전달 시 객체 전체 데이터를 스택에 **복사**.
  * **문제점**: 구조체/클래스 크기가 크면 **복사 비용(Copy Cost)** 및 메모리 오버헤드 발생.
* **참조 전달 (`const FVector& Vector`)**:
  * **원리**: 원본 객체의 **메모리 주소(8 bytes)**만 넘김.
  * **최적화**: 복사 비용 제로, `const` 키워드를 붙여 원본 데이터의 훼손(Side-Effect)을 방지.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 기본 타입(`int32`, `float`, `bool`)도 `const int32&` 형태로 참조 전달하는 것이 이득인가요?**
* **A**: 아니요, 기본 타입은 **값 전달(`int32`)이 더 유리**합니다. 64비트 아키텍처에서 주소값(포인터/참조)의 크기는 **8 바이트**인데, `int32`는 **4 바이트**입니다. 데이터 자체보다 주소값의 크기가 더 크므로, 주소를 경유하는 간접 참조 비용만 추가 발생하게 됩니다.

## 4. CDO (Class Default Object)

### 📌 핵심 정리
* **개념**: 엔진 초기화 시점에 각 `UClass`마다 **단 하나만 생성**되는 마스터 기본 객체.
* **목적**: 
  * **메모리 최적화**: 신규 액터 생성 시 CDO의 메모리 블록을 **Fast Binary Copy**하여 기본값 빠르게 복사.
  * 프로퍼티 초기값 및 `CreateDefaultSubobject` 컴포넌트 템플릿 기준점 제공.
* **주의사항**: CDO 수정 시 해당 클래스를 바탕으로 생성되는 향후 모든 객체의 기본값에 영향을 줌.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. CDO 시스템을 활용했을 때 액터 생성(Spawn) 시 얻는 대표적인 성능적 이점은 무엇인가요?**
* **A**: 액터 스폰 시 매번 생성자 로직 전체를 다시 실행하거나 에셋을 재로드하지 않고, 이미 완성된 CDO의 메모리 상태를 **이진 복사(Memory Copy)** 방식으로 빠르게 할당할 수 있어 스폰에 따른 프레임 드랍(Spike)을 최소화합니다.

## 5. 스마트 포인터 & UPROPERTY() GC (Garbage Collection)

### 📌 핵심 정리
* **UObject 관리 (`UPROPERTY()`)**:
  * `UObject` 계열은 C++ 표준 스마트 포인터 사용 금지.
  * **`UPROPERTY()`**를 명시하여 언리얼 **리플렉션 시스템(Reflection System)** 및 GC 가비지 컬렉션의 추적 대상(Ref Count / Reachability)으로 등록.
* **Non-UObject C++ 일반 객체 관리**:
  * `TSharedPtr` / `TSharedRef`: 레퍼런스 카운팅 기반 일반 C++ 클래스 공유 스마트 포인터.
  * `TWeakPtr`: 순환 참조(Circular Reference) 방지용 약한 참조.
  * `TUniquePtr`: 단일 소유권 전용 포인터.
* **`TWeakObjectPtr<T>`**: `UObject` 계열 전용 약한 참조 (GC 수거 방지 없이 **댕글링 포인터** 검출 가능).

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 댕글링 포인터(Dangling Pointer)란 무엇이며, `TWeakObjectPtr`는 이를 어떻게 방지하나요?**
* **A**: 
  * **댕글링 포인터**: 이미 메모리 해제(Free/GC)되어 유효하지 않은 주소를 포인터 변수가 계속 가리키고 있는 상태를 말합니다. 접근 시 크래시를 유발합니다.
  * **방지 방식**: `TWeakObjectPtr`는 참조 대상 `UObject`가 GC에 의해 수거되면, 포인터 내부 주소를 **자동으로 `nullptr` 처리**합니다. 따라서 접근 전 `.IsValid()` 검사로 안전성을 확보할 수 있습니다.

> **Q. `UObject` 포인터 멤버 변수에 `UPROPERTY()` 선언을 누락하면 어떤 문제가 생기나요?**
* **A**: 언리얼 GC가 해당 참조를 추적하지 못하므로, 해당 객체를 사용 중임에도 불구하고 **루트 세트(Root Set)에서 도달 불가능한 객체로 판단하여 GC가 메모리에서 강제 수거**할 수 있습니다. 이로 인해 댕글링 포인터가 발생하고 크래시로 이어집니다.

## 6. 소프트 레퍼런스 vs 하드 레퍼런스 (Soft vs Hard Reference)

### 📌 핵심 정리
* **하드 레퍼런스 (`TObjectPtr<T>`, Direct Pointer)**:
  * **특징**: 해당 객체(Character, UI 등)가 로드될 때 참조된 에셋도 메모리에 **즉시 함께 로드(Synchronous Loading)**.
  * **단점**: 에셋 간 의존성이 복잡할 경우, 캐릭터 하나 로드 시 게임 전체 에셋이 메모리에 연쇄적으로 올라가는 **메모리 폭발** 발생.
* **소프트 레퍼런스 (`TSoftObjectPtr<T>`, `FSoftObjectPath`)**:
  * **특징**: 에셋의 **경로 문자열(Path)**만 보유하고 있다가, 실제 필요한 시점에 **비동기 로딩(StreamableManager / Async Load)** 수행.
  * **목적**: 초기 로딩 시간 단축 및 메모리(RAM) 점유율 최적화.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 소프트 레퍼런스로 지정된 에셋을 실제 게임 내에서 사용할 때는 어떤 단계를 거쳐야 하나요?**
* **A**: 바로 멤버에 접근할 수 없으며, `FStreamableManager`를 통해 해당 에셋 경로를 **비동기 로드(AsyncLoad)** 요청해야 합니다. 로드가 완료된 콜백 시점에 `.Get()` 또는 `.LoadSynchronous()`를 호출해 메모리에 올려진 pointer를 얻어 사용합니다.

## 7. 델리게이트 (Delegate) & Event Driven Architecture

### 📌 핵심 정리
* **개념**: 객체 간의 결합도(Coupling)를 낮추는 **발행-구독(Publish-Subscribe) 패턴** 기반 콜백 구조.
* **종류**:
  * **단일 델리게이트 (Single Cast)**: 1개 함수만 바인딩 (`Execute`).
  * **다중 캐스트 델리게이트 (Multi Cast)**: 여러 함수 바인딩 및 일괄 실행 (`Broadcast`).
  * **다이나믹 델리게이트 (Dynamic Multi Cast)**: **블루프린트 연동 및 직렬화 가능** (속도는 일반 델리게이트보다 상대적으로 느림).
* **장점**: Character가 UI나 Sound, Particle 클래스를 직접 `#include`하지 않고도 상태 변화 알림 전달 가능.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 일반 다중 캐스트 델리게이트와 다이나믹 다중 캐스트 델리게이트의 성능적 차이 및 활용 목적은 무엇인가요?**
* **A**: 일반 델리게이트는 C++ 함수 포인터 기반으로 빠른 실행 속도를 가집니다. 반면 다이나믹 델리게이트는 언리얼 리플렉션 시스템을 거치므로 실행 속도가 다소 느리지만, **블루프린트 이벤트와 직접 연결 가능하며 데이터 직렬화가 가능**하다는 특징이 있습니다.

## 8. TArray vs TSparseArray vs TMap / TSet (UE5 컨테이너)

### 📌 핵심 정리
* **`TArray`**:
  * 연속된 메모리 블록(Contiguous Memory Allocation).
  * **캐시 적중률(Cache Hit Rate)**이 매우 높아 반복문 순회 시 최상의 성능. 중간 요소 삭제 시 인덱스 당김 비용 발생.
* **`TSparseArray`**:
  * 요소가 삭제되어도 메모리 구멍(Gap)을 유지하여 인덱스 안정성을 보장하는 희소 배열.
  * 삭제 비용 $O(1)$ 및 인덱스 고정 보장.
  * 단, 삭제된 원소의 Raw Pointer를 계속 참조하면 댕글링 포인터가 발생하므로 TWeakObjectPtr 연동 필수.
* **`TSet` / `TMap`**:
  * 해시 테이블(Hash Table) 기반 ($O(1)$ 접근).
  * 내부적으로 TSparseArray를 기반 구조로 사용하여 빠른 노드 할당/해제 지원.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. `TArray`가 메모리 상에서 왜 캐시 적중률(Cache Hit Rate)이 높고 순회 성능이 뛰어난가요?**
* **A**: CPU는 RAM에서 데이터를 가져올 때 요청된 주소 부근의 데이터를 공간 국소성(Spatial Locality) 원리에 따라 L1/L2 캐시 메모리로 함께 끌어옵니다. `TArray`는 요소들이 **메모리에 연속적으로 배치**되어 있으므로 다음 요소 접근 시 캐시에 이미 올려져 있을 확률(Cache Hit)이 극대화되어 속도가 빠릅니다.

> **Q. TSparseArray는 삭제 시 인덱스를 당기지 않는데, 댕글링 포인터 문제는 어떻게 발생하고 예방하나요?
* **A**: 원소 삭제 후 기존 메모리 주소를 가리키는 Raw Pointer(원시 포인터)를 그대로 접근하면 댕글링 포인터 및 메모리 오염이 발생합니다. TSparseArray 자체가 포인터 유효성을 보장해주지는 않으므로, UObject 계열은 TWeakObjectPtr를 사용해 GC 및 삭제 시 자동으로 nullptr 변환이 되도록 안전 장치를 구성해야 합니다.

## 9. Lvalue vs Rvalue & 이동 언어학 (Move Semantics)

### 📌 핵심 정리
* **Lvalue (좌측값)**: 이름이 있고, 메모리 주소를 취할 수 있으며, 단일 표현식을 넘어 지속되는 변수.
* **Rvalue (우측값)**: 이름이 없고, 표현식 연산 직후 사라지는 **임시 객체(Temporary Object)**.
* **이동(Move) 연산 (`MoveTemp`)**: 
  * 깊은 복사(Deep Copy) 대신, 임시 객체의 **메모리 소유권(주소)만 신규 객체로 이전**하여 복사 비용 제로화.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. C++에서 `MoveTemp`(또는 `std::move`)를 사용하는 목적과 동작 방식은 무엇인가요?**
* **A**: 곧 소멸될 임시 객체나 Rvalue 데이터의 동적 할당 자원(포인터 주소)을 새 객체로 **소유권 재지정**만 수행하는 방식입니다. 대용량 배열이나 문자열 전달 시 발생하는 비싼 깊은 복사(Deep Copy) 연산을 원천 차단하여 성능을 최적화합니다.

## 10. 직렬화 (Serialization) & FArchive

### 📌 핵심 정리
* **개념**: 메모리 상의 C++ 객체 데이터를 저장/전송 가능한 형태의 **연속적인 바이트 스트림(Byte Stream)**으로 변환하거나 역변환하는 과정.
* **UE5 구현**: `FArchive` 클래스 및 `operator<<` 연산자를 사용하여 저장(Save)과 로드(Load) 로직을 단일 코드 구조로 처리.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 언리얼 `FArchive` 사용 시 하나의 함수로 저장과 로드를 모두 처리하는 방식의 이점은 무엇인가요?**
* **A**: 데이터를 읽고 쓰는 로직의 순서나 구조가 불일치하여 생기는 데이터 오염 문제(Out of Sync)를 방지할 수 있으며, 코드 유지보수성을 극대화합니다.

## 11. 가상 함수 테이블 (VTable) & 다형성 (Polymorphism)

### 📌 핵심 정리
* **개념**: `virtual` 키워드가 선언된 가상 함수를 포함할 때, 실행 시점(Runtime)에 바인딩할 함수를 결정하기 위해 컴포넌트 내부에 생성되는 **함수 포인터 테이블**.
* **구조**: 해당 클래스의 객체 메모리 최상단에 `vptr`(가상 함수 테이블 포인터, 8 bytes)가 생성됨.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 가상 함수 호출 시 발생하는 간접 호출(Indirect Call) 비용과 메모리 오버헤드는 무엇인가요?**
* **A**: 객체당 `vptr`용 메모리(8 bytes)가 추가로 사용됩니다. 또한 함수 호출 시 `vptr`을 거쳐 `VTable`에서 실제 함수 주소를 조회한 뒤 점프하는 **2단계 간접 참조**가 발생하므로 CPU 캐시 미스 가능성이 높아지고 아주 미세한 지연이 생깁니다.

---

## 12. Reflection System (리플렉션) & USTRUCT vs UCLASS

### 📌 핵심 정리
* **개념**: C++ 프로그램이 **실행 중(Runtime) 자기 자신의 구조체, 클래스, 프로퍼티, 함수 정보를 조사하고 수정**할 수 있게 지원하는 시스템.
* **UCLASS**: GC 추적, 리플렉션 지원, 계층 구조 상속 가능, `UObject` 관리 대상.
* **USTRUCT**: 가벼운 데이터 묶음용, **GC에 의해 관리되지 않음**, 스택/힙 모두 할당 가능.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. `USTRUCT` 내부의 `UObject*` 포인터 변수에 `UPROPERTY()`를 붙이면 GC 추적이 작동하나요?**
* **A**: 네, `USTRUCT` 자체가 GC 대상은 아니지만, 해당 구조체 변수가 **`UCLASS` 내부의 `UPROPERTY()` 포인터나 컨테이너로 소유되어 있다면** 내부 `UPROPERTY()` 포인터도 GC 가비지 컬렉터의 추적 대상에 포함됩니다.

---

## 13. RAII (Resource Acquisition Is Initialization) 패턴

### 📌 핵심 정리
* **개념**: 자원(메모리, 스레드 락, 파일 핸들 등)의 소유권을 **객체의 생명주기(Scope)**와 일치시키는 디자인 패턴.
* **원리**: 객체 생성자에서 자원을 획득하고, 스택 탈출 등으로 소멸자가 호출될 때 자원을 **자동 해제**.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. C++ 멀티스레드 환경에서 `FScopeLock`은 RAII 패턴을 어떻게 활용하나요?**
* **A**: `FScopeLock` 생성 시 Mutex(크리티컬 섹션)를 잠그고, 해당 함수나 블록 scope를 벗어나는 순간 소멸자가 호출되며 **자동으로 Lock을 해제**합니다. 개발자의 예외 처리나 실수로 인한 Deadlock 발생 위험을 방지합니다.

## 14. 캐시 국소성 (Cache Locality: Temporal vs Spatial)

### 📌 핵심 정리
* **시간 국소성 (Temporal Locality)**: 최근 접근한 메모리 위치에 조만간 다시 접근할 가능성이 높은 특성 (예: 반복문 내부 변수).
* **공간 국소성 (Spatial Locality)**: 접근한 메모리와 인접한 위치의 데이터를 조만간 접근할 가능성이 높은 특성 (예: `TArray` 연속 배치).

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 게임 루프 성능 향상을 위해 공간 국소성을 극대화하는 컴포넌트 설계 방식은 무엇인가요?**
* **A**: 데이터 지향 아키텍처(DOD)를 도입하여, 포인터 기반의 파편화된 객체 배열 대신 관련 데이터를 연속된 메모리 배열(`TArray`) 구조로 몰아넣어 CPU 캐시 적중률을 최대로 끌어올리는 방식을 사용합니다.

## 15. Const Correctness (const 상수의 엄격성)

### 📌 핵심 정리
* **개념**: 함수 매개변수, 반환값, 멤버 함수에 `const`를 명확히 선언하여 **데이터 수정 불가 범위를 명시적(Compile-time)으로 제한**하는 작성 기법.
* **const 멤버 함수 (`void GetHealth() const;`)**: 해당 함수 내에서 클래스의 멤버 변수를 수정할 수 없음을 컴파일러가 보장.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. `const` 멤버 함수 내부에서 특정 멤버 변수의 값을 예외적으로 수정해야 한다면 어떤 키워드를 쓰나요?**
* **A**: **`mutable`** 키워드를 변수 선언 시 붙여주면, `const` 멤버 함수 내부에서도 해당 변수의 값을 수정할 수 있습니다. (예: 스레드 락용 Mutex, 캐싱 목적의 임시 변수)

## 16. UE5 틱 그룹 (Tick Group) & Execution Order

### 📌 핵심 정리
* **개념**: 한 프레임 내에서 액터 및 컴포넌트들의 **`Tick` 실행 순서를 단계별로 제어**하기 위한 그룹 체계.
* **주요 단계**:
  * `TG_PrePhysics`: 물리 연산 적용 전 (입력 처리, AI 판단).
  * `TG_DuringPhysics`: 물리 연산 실행 중 병렬 처리.
  * `TG_PostPhysics`: 물리 연산 완료 후 (카메라 추적, 캐릭터 위치 최종 동기화).

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 카메라인 SpringArm/CameraComponent의 틱 그룹을 플레이어 캐릭터 이동 로직보다 나중에 실행해야 하는 이유는 무엇인가요?**
* **A**: 캐릭터의 위치 업데이트가 완료된 후 카메라 위치를 계산하지 않으면, 한 프레임 이전 위치를 카메라가 추적하여 화면이 미세하게 떨리는 **Jittering(지터링) 현상**이 발생하기 때문입니다.

## 17. 언리얼 엔진 C++ 빌드 시스템 (UHT vs UBT)

### 📌 핵심 정리
* **UHT (Unreal Header Tool)**: C++ 헤더 파일의 `UCLASS()`, `UPROPERTY()` 등 언리얼 매크로를 분석하여 리플렉션용 코드(`.generated.h`)를 **자동 생성**.
* **UBT (Unreal Build Tool)**: 생성된 C++ 코드와 엔진 소스를 엮어 C++ 컴파일러(MSVC 등)를 호출하고 빌드를 총괄 조율하는 C# 기반 **빌드 도구**.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. `#include "FileName.generated.h"` 문장이 C++ 헤더 파일의 최하단 `#include`에 위치해야 하는 이유는 무엇인가요?**
* **A**: UHT가 헤더를 파싱할 때 헤더 상단에 선언된 클래스/프로퍼티 정보들을 기반으로 매크로 코드(`.generated.h`)를 생성합니다. 전처리기 단계에서 이 파일이 매크로 정의보다 먼저 포함되면 컴파일 에러가 발생하므로 반드시 최하단에 위치해야 합니다.

## 18. 인라인 함수 (Inline Function) & Direct Call

### 📌 핵심 정리
* **개념**: 함수 호출 시 점프(Call)하는 대신, 컴포넌트를 호출한 위치에 **함수 본문 코드를 직접 삽입(Inlining)**하도록 컴파일러에 요청하는 제어자.
* **장점**: 함수 호출에 따른 스택 프레임 생성, 매개변수 복사, 반환 주소 저장 등 오버헤드 제거.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. `inline` 키워드를 붙여도 컴파일러가 인라이닝을 거부하는 대표적인 경우는 언제인가요?**
* **A**: 함수 내부 코드가 너무 길거나, 재귀 호출(Recursive Call)을 사용하거나, 가상 함수(`virtual`)여서 실행 시점 결정(Dynamic Binding)이 필요한 경우에는 컴파일러가 인라이닝을 수행하지 않습니다.

## 19. 멀티스레딩 & FRunnable / Task Graph System

### 📌 핵심 정리
* **`FRunnable`**: 장시간 독립적으로 작동하는 **전용 스레드(Worker Thread)**를 직접 생성하고 제어할 때 사용.
* **Task Graph**: 짧고 단위가 작은 작업(Task)들을 **의존성 그래프 구조로 묶어 엔진 스레드 풀에 비동기 분배/실행**하는 시스템.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 비동기 Worker 스레드 내부에서 `UObject`를 직접 생성(`NewObject`)하거나 레벨 내 액터를 수정하면 안 되는 이유는 무엇인가요?**
* **A**: 언리얼의 `UWorld`, `UObject` 생성, Rendering, GC 등 핵심 엔진 프레임워크 로직은 **메인 스레드(GameThread)에 단일 소유권**이 맞춰져 있습니다. 타 스레드에서 직접 수정 시 동시성 경쟁(Race Condition) 및 메모리 오염으로 즉시 크래시가 유발되므로, 비동기 완료 후 결과를 GameThread로 전달해 변경해야 합니다.

## 20. 메모리 파편화 (Memory Fragmentation) & FMemory / FMalloc

### 📌 핵심 정리
* **개념**: 메모리의 할당과 해제가 반복되면서 Total 가용 메모리는 충분하지만, **연속된 메모리 공간이 부족하여 새로운 메모리 할당에 실패**하는 현상 (외부 파편화).
* **UE5 대응**: 자체 메모리 할당자(`FMallocAnsi`, `FMallocBinned`)를 탑재하여 크기별 메모리 블록(Bin)을 미리 확보하고 관리함으로써 파편화를 방지.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 게임 개발 중 메모리 파편화를 유발하는 대표적인 코드 패턴과 이를 예방하는 방법은 무엇인가요?**
* **A**: 
  * **원인**: 런타임 게임 루프 동안 다양한 크기의 객체를 `new`/`delete`로 빈번하게 동적 할당/해제하는 패턴입니다.
  * **예방법**: 객체 풀링(Object Pooling) 패턴을 적용하여 메모리를 미리 할당받아 재사용하거나, 배열 용량을 사전에 확보하는 `TArray::Reserve()`를 사용하여 재할당 발생을 억제합니다.

## 21. Unreal Network Replication & RPC

### 📌 핵심 정리
* **`UPROPERTY(Replicated)`**: 
  * **목적**: 체력, 탄약, 상태 등 **지속적인 변수 데이터(State)**를 서버에서 클라이언트로 동기화.
* **RPC (`Server`, `Client`, `NetMulticast`)**: 
  * **목적**: 발사, 상호작용 등 **일회성 이벤트(Event)** 호출 및 명령 전달.
* **클라이언트 예측 (Client Prediction)**: 
  * 네트워크 핑(Latency)으로 인한 조작 지연감을 없애기 위해 클라이언트가 선제적으로 로직(애니메이션/이펙트)을 실행하고, 이후 서버 판정 결과로 교정(Reconciliation)하는 기법.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 클라이언트에서 총을 쏠 때, 왜 `Server` RPC만 보내고 기다리지 않고 클라이언트 예측을 수행하나요?**
* **A**: 서버 검증 결과만 기다린 후 연 연출을 틀면 왕복 네트워크 지연(RTT) 때문에 입력과 화면 반응 사이에 시차가 발생하여 조작감이 극도로 악화됩니다. 따라서 클라이언트가 먼저 이펙트와 애니메이션을 선제 실행(Prediction)하고, 이후 서버 판정 결과가 도착하면 위치나 상태를 보정(Reconciliation)하여 즉각적인 조작감을 확보합니다.

## 22. Collision Channels & Trace (충돌 및 트레이스)

### 📌 핵심 정리
* **LineTraceSingleByChannel**: 
  * **기준**: 설정된 **반응 방식(Ignore / Overlap / Block)**의 채널 집합을 기준으로 충돌 검사.
* **LineTraceSingleByObjectType**: 
  * **기준**: 콜리전의 **물성 유형(Static, Dynamic, Pawn 등)** 자체를 기준으로 충돌 검사.
* **최적화 방향**: 씬 내부 오브젝트가 많을수록 복잡한 Mesh Collision 대신 단순화된 Simple Collision(Box/Sphere) 사용 필수.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 씬에 오브젝트가 10,000개 이상 배치되어 있을 때 LineTrace 성능 저하를 막으려면 어떻게 최적화해야 하나요?**
* **A**: Complex Mesh(정밀 메쉬) 검사를 피하고 **Simple Collision(Box/Sphere)**을 활용합니다. 또한 트레이스 채널 반응(Response)을 최대한 Ignore로 설정하여 검사 대상을 줄이고, BVH(Bounding Volume Hierarchy) 공간 분할을 통해 불필요한 바운딩 박스 연산을 차단합니다.

## 23. UE5 Rendering Pipeline & Draw Call Optimization

### 📌 핵심 정리
* **Draw Call**: CPU가 GPU에게 "이 메쉬와 재질을 그려라"라고 보내는 렌더링 명령 단위. 발생 횟수가 많을수록 CPU 렌더링 오버헤드 급증.
* **최적화 기법**:
  * **Instanced Static Mesh (ISM / HISM)**: 동일 메쉬를 하나의 Draw Call로 묶어 그리기.
  * **Nanite**: 가상화된 폴리곤 스트리밍을 통해 LOD 작성 없이 실시간으로 메쉬 세밀도를 제어하고 Draw Call을 자동 최적화.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. Nanite와 Lumen의 도입으로 기존 LOD 및 Static Light Baking 작업 방식은 어떻게 변화했나요?**
* **A**: 과거에는 수작업으로 LOD를 제작하고 텍스처에 광원을 구워내는(Lightmass Baking) 작업이 필수적이었으나, Nanite를 통해 수백만 폴리곤 메쉬의 LOD 자동화 및 가상화가 가능해졌고, Lumen을 통해 실시간 글로벌 일루미네이션(GI)이 처리되어 텍스처 베이킹 과정 없이 고품질의 동적 조명을 연산할 수 있게 되었습니다.

## 24. Smart Pointer: TSharedPtr vs TSharedRef

### 📌 핵심 정리
* **`TSharedPtr`**: 
  * **특징**: `nullptr`을 가질 수 있는 일반적인 공유 스마트 포인터. 접근 전 유효성 검사(`.IsValid()`) 필수.
* **`TSharedRef`**: 
  * **특징**: **절대 `nullptr`이 될 수 없음을 보장**하는 강한 참조 스마트 포인터.
  * **장점**: Null Check 연산 오버헤드를 원천 차단하여 코드 안전성 및 가독성 확보.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. `TSharedRef`를 `nullptr`로 초기화하려고 하거나, 참조하던 객체가 소멸하면 어떻게 되나요?**
* **A**: `TSharedRef`는 `nullptr` 할당 자체가 컴파일 에러를 유발합니다. 또한 참조 대상 객체는 레퍼런스 카운트가 0이 되지 않는 한 메모리에서 해제되지 않으므로, 참조가 유지되는 동안 댕글링 포인터나 유효하지 않은 메모리 접근이 일어나지 않습니다.

## 25. GAS (Gameplay Ability System) 아키텍처

### 📌 핵심 정리
* **`GameplayAttribute`**: HP, MP, 이동속도, 공격력 등 캐릭터의 수치적 스탯 데이터를 저장 및 관리.
* **`GameplayEffect`**: 스탯을 변경하거나 버프/디버프, 데미지 연산을 적용하는 데이터 중심 로직 단위.
* **역할 분담 이유**: 데이터(Attribute)와 로직(Effect)의 완전한 디커플링(Decoupling)을 통한 유연성 확보.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 체력 감소 시 Attribute 수치를 직접 수정하지 않고 `GameplayEffect`를 거쳐서 변경해야 하는 이유는 무엇인가요?**
* **A**: 클라이언트 예측(Prediction), 네트워크 동기화(Replication), 데미지 저항 계산(Execution Calculation), 버프/디버프 중첩 및 방어력 공식 적용 등의 공통 도메인 로직을 한 곳에서 안전하게 처리하고, 데이터 오염 없이 일관성을 유지하기 위함입니다.

## 26. 크래시 디버깅 & Call Stack 분석

### 📌 핵심 정리
* **주요 도구**: Call Stack, `.dmp` (Crash Dump File), PDB (Symbol File).
* **분석 절차**:
  1. 덤프 파일과 해당 빌드의 PDB 파일을 연결하여 Call Stack 복원.
  2. 크래시 발생 지점의 변수 메모리 주소 확인 (`0x00000000` = Null Pointer Dereference).
  3. 필요시 AddressSanitizer(ASan), Unreal Insights, `MemReport` 도구를 활용해 메모리 오염 추적.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. 빌드 환경에서 소스 코드 없이 덤프 파일(.dmp)만으로 런타임 Crash 위치를 추적하려면 무엇이 필요한가요?**
* **A**: 해당 빌드가 생성될 때 함께 출력된 **PDB(Program Database) 기호 파일**이 필수적입니다. PDB가 있으면 기계어 주소값을 C++ 함수 이름과 코드 줄 번호로 복원(Symbolication)하여 정확한 크래시 지점과 변수 상태를 파악할 수 있습니다.

## 27. C++ Virtual Destructor (가상 소멸자)

### 📌 핵심 정리
* **원리**: 부모 클래스의 소멸자에 `virtual`을 명시해야, 부모 포인터로 자식 객체를 가리키다 해제할 때 **자식 소멸자 $\rightarrow$ 부모 소멸자** 순으로 정상 호출됨.
* **위험성**: `virtual` 누락 시 부모 소멸자만 호출되어 자식 클래스 내부 동적 할당 자원의 **메모리 누수(Memory Leak)** 발생.

### ❓ 예상 꼬리질문 & 면접용 대답

> **Q. `UObject`를 상속받는 언리얼 C++ 클래스 작성 시에도 소멸자에 `virtual` 키워드를 매번 붙여야 하나요?**
* **A**: 아니요, 붙이지 않아도 됩니다. 언리얼 엔진 최상위 기반 클래스인 `UObjectBase` 레벨에서 이미 소멸자가 `virtual`로 선언되어 있으므로, 이를 상속받는 모든 `UObject` 계열 클래스들은 자동으로 가상 소멸자 특성을 가집니다.
